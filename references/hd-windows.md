# Codex 桌面多窗口生图高清

主对话负责裁切、并行派发、跟进和收图。每个新建的可见会话负责一个编号的生图并原样保存结果。桌面工具和文件共享可用时，用 `hd-batch --run RUN --capability CAP` 领取，固定分发到新会话。已领取批次使用原调度记录续接，避免重复生图。

## 1. 查找桌面工具和归组

本页只用于 windows 批次。用户已看到本版小样和“1｜多窗口并行制作（新开六个制作聊天）”的说明，随后单独回复 1 就是本次明确建聊请求，直接执行，无需再确认。宿主不支持或拒绝时报告真实阻碍，保留任务。

先在工具目录定位当前桌面 `create_thread`、`wait_threads` 和窗口定位所需的 `list_threads`。有现成项目时使用 `list_projects` 核实项目 ID，六个新会话都在同一项目以 local 方式创建。普通聊天以 projectless 方式创建，再用 `create_sidebar_section` 和 `move_thread_to_sidebar_section` 归入本次产品组。组名为「商品名 · 高清制作」，重复商品运行可加短运行编号。将本轮分区的 `sectionId` 与真实创建回执立即登记到同一 run，供清理或恢复使用。侧栏归组失败时保留已创建的会话，记录真实失败并继续收图。

第一次创建前，在主对话发一条普通进度消息：「**开始制作 6 张高清图。** 左侧会出现『高清子任务 01–06』，每个会话负责一张，都属于本次制作。制作期间请先保留这些会话，成品会在这里统一交付。」

## 2. 一次领取、先派发再等

1. 按 [高清制作](hd-production.md) 完成授权和裁切，再领取六项任务。工具明确限制并发时用 `capability.max_concurrency` 登记，未知时默认六个任务可派发，服务的实际生图调度由平台决定。
2. 用 `hd-window-status --run RUN` 读取状态及空位。按编号顺序用 `hd-window-reserve --run RUN --index N --attempt A` 预留每个可用空位，取得各自 title 和 prompt。预留逐次执行以保护记录。
3. 将当前全部已预留会话的独立 `create_thread` 调用并发提交。使用预留的 `title` 和完整任务消息，**发完这批开窗请求再等待生图**。逐项保留原创建回执。收到对应的真实 `hostId` 和 `threadId` 后，立即用 `hd-window-bind --run RUN --index N --attempt A --host HOST --thread THREAD --origin create_thread` 绑定。只有 `clientThreadId` 时在原 run 保存该回执，按宿主实际返回追踪至正式 ID 再绑定。绑定后按同一 ID 调用 `set_thread_title` 使用预留记录的 `display_title`，例如「高清子任务 01｜营销首图」。短批次码和尝试号用于绑定前定位。
4. `wait_threads` 用真实 hostId、threadId 和最新游标，一次等待所有活跃会话，单次等待至多 60 秒。有空位继续派发。收到文件后以同一 run 的结果收据为准。回件列表按原编号交付，包含有结果的全部编号。成图交给用户审图。
5. 核对派发时只查看会话和执行时间记录。只有多项调用启动时间重叠，才能对用户描述已并行发起。服务端同时计算的数量以其可观测能力为准。

## 3. 续接原会话和回件

`ready` 按计划派发。预留后未绑定的 `locate_thread` 优先跟踪已保存的创建回执。用预留标题寻址时，核对聊天执行的是同一 run 的同一任务。缺少该聊天的真实创建回执时绑定省略 `--origin`，该会话不进入自动归档名单。只有工具明确证实原请求未创建，才复用预留进行创建。`waiting`、`running`、`unknown` 都查询原任务。已返回但未保存时，同一执行会话恢复原回件登记。`saved` 由主对话直接交付。`failed` 记录具体原因。用户明确指出一张要改时，走单张修复路径。

## 4. 主对话交付后的侧栏清理

1. `hd-finish` 发布文件后，先在主对话发送用户可见的交付消息，按[高清制作](hd-production.md)逐张展示并提供目录链接和完整路径。用发送后可继续执行工具的普通进度消息展示整套交付。若宿主只在最终回复提供可见交付，先交付并登记待归档清单，下一次本轮主对话能执行工具时续接。文件保存和工具回执只是交付前的准备。
2. 整批已汇报且没有待回件时，刷新同一 run 的调度记录和桌面状态。只收尾已结束且有真实创建回执的会话。`thread.created_for_run` 必须等于当前运行编号。使用该绑定中的真实 `hostId`、`threadId`，明确排除主对话、旧批次、仅按标题找回的会话和用户原有聊天。仍在运行或状态不确定的会话保留并继续跟踪。
3. 对满足条件的会话逐个调用 `set_thread_archived`，显式传入 `hostId`、`threadId` 和 `archived: true`。在 run 内记录成功 ID，续接跳过已完成项。归档失败时保留该条，报告实际状态。
4. 归档成功回执可能先于 `list_threads` 更新分区成员。使用 [分区清理函数](../scripts/sidebar-cleanup.mjs) 完成检查、删除和验证。传入本 run 创建回执中的 `sectionId`，以及已按步骤 2–3 核验归属且收到 `archived: true` 的聊天成员键（`codex:thread:<hostId>:<threadId>`）。同时运行多个批次时，各自只使用自己的记录。分区有成员且均为已归档的本批聊天时，分别等 2、5、10 秒重新查询；看到其他成员就保留分区。只有查到成员为空才提交删除，删除后也查询分区是否已消失。
5. 宿主读取上述函数并在同一次工具编排中执行。`list` 调用 `list_threads`（普通 recent 模式，`limit: 1`），`remove` 调用 `delete_sidebar_section({sectionId})`，均解码工具真实 JSON 文本，工具报错则抛出；`wait` 使用宿主计时。保存返回的完整结果为同一 run 的 `desktop-section-cleanup.json`。`deleted` 或 `absent` 表示已确认分区消失；`retained` 或 `pending` 需报告具体原因。续接同一 run 时读取旧创建、归档和清理回执，跳过已有成功归档，从分区检查继续；有成功删组回执也以实际查询确认。没有创建回执时保留分区。交付回报分别说明聊天归档数和分区清理结果。用户可从归档找回制作会话，原始回件和正式成品均保留。
